## Lens 4 — Regression-Across-Screens ("Does the same input produce the same number everywhere, and did this break another view?")
### Critical
- None.
### Improvement
- **Row 7 ordering is sufficient — verified against the nanostores re-entrancy model, not just asserted.** `[verified — source + nanostores internals read; test RUN]` This is the task's sharpest question, so I traced it concretely. The Step 4 `onChange` does two sequential `setKey`s: `hasModifiedContrib=true` (Step4:177) THEN `monthlyContrib=value` (Step4:178). nanostores `notify` (atom/index.js:42-63) uses a queue: a `setKey` whose `notify` fires *while a listener is already running* is appended to `listenerQueue` (not run recursively), and the queue is drained with the store value **as it stood when each item was pushed**. Trace: (1) `setKey('hasModifiedContrib', true)` → queue empty → subscriber runs with `hasModifiedContrib === true` → the sync guard `!val.hasModifiedContrib` (financialPlan.ts:94) is false → **sync skipped**; the subscriber's own seed `setKey`s queue and re-run, each still seeing the guards hold. (2) `setKey('monthlyContrib', value)` → fresh notify → subscriber runs with `hasModifiedContrib === true` → sync skipped again → the hand-entered value survives. **The flag-before-value ordering is load-bearing and correct; reversing it would re-clobber.** There is **no re-entrant path** where the subscriber's `setKey('monthlyContrib', totalInvest)` fires before the flag is set, because the flag write completes (and drains) before the value write begins. The row-7 test passed. The engineer's `errors.md` row-7 entry records a live Claude_Preview confirmation ($1,000 auto-seed → hand-entered $2,500 → Step-1 bump to $1,500 → stayed $2,500). I rely on that recorded live evidence; I could not re-run it (preview denied).
- **`hasModifiedContrib` is never resettable — a deliberate, defensible one-way latch, but a mild UX trap with no escape hatch.** `[code-derived]` Set `true` in exactly one place (Step4:177), never set back to `false` anywhere, and persisted to localStorage. So once a user types *any* value into the Step 4 contribution field (even a typo they then clear), the Step-1 → contribution auto-seed is permanently off for that browser. This is intentional (Pattern 5 / lesson 5: "seed defaults, then let user input win"), and it mirrors `hasModifiedRetirement` (also never reset, also accepted). The trade-off is correct — silently re-clobbering would be the actual row-7 bug. But there is now **no UI affordance to re-sync to the Step 1 sum**, and no hint that the field has "detached" from Step 1. A user who later overhauls their Step 1 investment lines expecting the contribution to track will find it frozen and silent. Recommend (Improvement, low severity): either a tiny "↻ reset to Step 1 total" link next to the field when `hasModifiedContrib && monthlyContrib !== totalInvest`, or at minimum a one-line helper ("You've set this manually; it no longer follows Step 1"). Same treatment would benefit `hasModifiedRetirement`. This is a product decision, not a bug.
- **Step 4 and Step 5 use different `planReady` evaluations of the *same* `res.annualRetSpend` — consistent today, but two copies of the gate.** `[code-derived]` Both compute `planReady = res.annualRetSpend > 0` locally (Step4:150, Step5:221). Same store value → same result, so no divergence now. It's a minor Pattern-1-adjacent smell (the "is the plan ready?" predicate is defined twice in two components rather than once on the store). If the readiness definition ever changes (e.g. "ready" should also require `monthlyContrib > 0`), the two screens could drift. Low severity; consider exposing `res.planReady` from the engine so both screens read one source. Polish.
- **The Step 4 outcome-strip neutralization does not introduce a status-by-color-alone (WCAG 1.4.1) issue.** `[code-derived]` When `!planReady`, the value goes grey (`#cbd5e1`, Step4:547) AND the `✓ on track`/`✗ shortfall` verdict line is removed entirely (`{planReady && ...}`, Step4:557). Pattern 4 compliant. (Confirming the rendered grey on screen is the one `[NEEDS-LIVE]` item, but the code path is unambiguous.)
