# Audit: Step 2 — Retirement Design v1
# Auditor: finplan-auditor | Date: 2026-06-08

## Verdict
**Revise.** Step 2 is the cleanest screen of the set on engine discipline — it writes 11 slider values to the store and reads `res.totalAllocated` back, recomputing nothing the engine owns except one harmless local sum. No false-rigor language, no dead `*-shiny-*` utilities, every input labeled. The two issues that block a clean ship are both presentation:

1. **Off-canonical violet `#8b5cf6` is the "retirement" series color, and one use renders as failing text (`Step2_RetirementDesign.tsx:181, 199, 135`).** Violet-500 is **not in canonical §6 at all** (the palette has no purple). It paints the "Retirement" chart bar (decorative — acceptable), but also the **"Retirement Monthly" summary-strip value** (`:199`, ~17px bold) — and `#8b5cf6` on the `#0f172a`-ish strip computes to ≈ **3.83:1**, which **fails WCAG AA for normal text** (canonical §7). The copy "Blue = today, violet = retirement" (`:135`) hard-codes the off-canonical hue into the explanation. Designer must either add violet to canonical §6 with a role and a contrast verdict, or replace it with a canonical accent.
2. **The 11 retirement sliders carry `aria-label` but no visible "why."** `RangeSlider` supports `helperText` (`RangeSlider.tsx:104-106`), but Step 2 passes **none** to any of the 22 slider instances (`grep helperText` → 0 hits). The screen's whole premise — "some costs drop, others rise" — is explained once in the intro card's smart-defaults list (`:120-126`), then each individual slider gives the user only "Today: $X" + a "+30% vs today" delta (`:273-277`), with no per-slider reason ("healthcare rises with age," "no daily commute"). A first-timer adjusting Healthcare sees the number but not why the default moved it. The "why" exists in the engine's seeding logic and the intro, but not at the point of decision.

Neither touches a number's correctness. Step 2's calculations are sound; the gaps are palette-canon and educational-surfacing.

**Composite: 7/10.** (Highest of the set — strong engine hygiene; loses points on the violet contrast fail and the missing per-slider rationale.)

## Lens 1 — Nervous First-Timer ("Would someone who's never planned understand and trust this?")
### Critical
- **No per-slider "why" at the point of decision.** The 11 sliders give "Today: $X" + a "+30% vs today" delta, but the *reason* the default moved (healthcare rises with age, transport drops with no commute) lives only in the intro card's bullet list (`:120-126`) — four reasons for 11 sliders, and the user scrolls past it before reaching the sliders. `RangeSlider` has a `helperText` slot that is unused on every one. A nervous first-timer adjusting "Healthcare +30%" has no inline explanation of why, and the screen's entire teaching premise ("spending shifts in retirement") is the thing being under-surfaced. This is the screen's biggest first-timer gap and the most actionable. `[NEEDS-LIVE]` to confirm the intro-to-slider scroll distance.
### Improvement
- **The "Increase/Decrease" delta strip can confuse before the plan is built (`:200-204`).** `delta = retMonthlySpend − res.totalAllocated`. When retirement sliders are still seeding (or a category was zeroed), the strip can show a large "Decrease" that looks like an error to someone who hasn't yet understood that the comparison is retirement-vs-now. The color logic also inverts intuition: an **increase** is amber (`#f59e0b`, "approaching limits") and a **decrease** is green (`#10b981`) — defensible (spending less is "good") but unexplained, and amber-for-more-spending may read as a warning the user didn't trigger. A one-line caption would help.
- **"Misc" categories silently merge and drop fields (consistency with Step 5's same issue).** `currentValues.misc = i.tech + i.homeImp + i.misc` (`:44`) **omits `i.subscriptions`**, which the engine's seeding includes (`financialPlan.ts:76`: `misc = tech + homeImp + subscriptions + misc`). So the "Today" Misc bar understates what actually seeded `retMisc`. A user comparing the Misc bars sees a "Today" number lower than the value the slider was seeded from. Minor, but it is a today-column understatement (same family as the Step-5 "Now vs Retirement drops categories" finding).
- **Fixed vs Discretionary split uses "Discretionary," not the Sethi term.** The discretionary card header (`:299`) reads "Discretionary Spending in Retirement." The glossary mandates **"Guilt-Free Spending"** and bans "discretionary" explicitly. See Lens 3 — this is a glossary violation, flagged there; from the first-timer lens it also loses the non-judgmental Sethi framing the product is built on.

## Lens 2 — Skeptical CFP ("Is the math correct, defensible, and cited?")
### Critical
- None. Step 2 makes no financial *claim* — it captures retirement-spend inputs and shows a current-vs-retirement comparison. The smart-default percentages it describes (Healthcare +30%, Transport −50%, Entertainment +20%, Debt −80%, `:122-125`) match the engine's seeding multipliers (`financialPlan.ts:79-88`: ×1.3, ×0.5, ×1.2, ×0.2) — so the copy is **accurate to the code**, which is the CFP-relevant check here.
### Improvement
- **The smart-default multipliers are presented as fact with no source or "rule of thumb" framing.** "Healthcare: +30% (medical costs rise with age)" etc. are reasonable heuristics, but they are the tool's own assumptions, not cited (unlike the WR brackets, which name Trinity). Canonical does not lock these seeding multipliers with a source either. A CFP would want them framed as adjustable starting estimates ("a common starting point — adjust to your situation"), which the intro *almost* does ("Sliders start from your current spending — adjust each"). Low severity; the sliders are user-editable so no number is forced.
- **Transport −50% and Debt −80% are applied to the *current* value, but the intro lists them as flat rules.** Defensible (they ARE percentage adjustments), and the per-slider delta shows the resulting %, so a user can see the actual effect. Not an error; noting for completeness.

## Lens 3 — Trust & Credibility ("Does any label claim more rigor or certainty than the math delivers?")
### Critical
- **Glossary violation: "Discretionary Spending" instead of "Guilt-Free Spending" (`:299`).** The glossary table bans "discretionary" / "wants" / "non-essential" and mandates Sethi's **"Guilt-Free Spending"** as the canonical phrase — this is load-bearing product language the Content agent owns and the Auditor checks. The Fixed Costs card uses the correct "Fixed Costs" term (`:246`); the discretionary card breaks the pair. (Note: the engine's three-bucket budget is Fixed / Investments / Guilt-Free; Step 2 is splitting retirement spend into Fixed vs lifestyle, so there's no "Investments" bucket here — but the lifestyle bucket must still use the Guilt-Free term, not "Discretionary.") This is the one clear honest-labeling defect on the screen.
### Improvement
- **Off-canonical violet `#8b5cf6` as the retirement series (Pattern 3 / canonical §6-7).** Used at `:181` (chart "Retirement" bar — decorative, OK), `:199` (the "Retirement Monthly" summary value — **text, 3.83:1, fails AA normal**), and named in the legend copy "violet = retirement" (`:135`). Violet is absent from canonical §6 entirely. The Step-5 audit flagged the identical purple drawdown hue; this is the same drift, now also driving a chart series and a failing text label. Decision needed: add violet to §6 with a role + contrast note, or swap to a canonical accent (e.g. `#10b981` success or `#f59e0b` warning for the "retirement" series, both AA-safe as text).
- **`#cbd5e1` (slate-300) on the chart Y-axis ticks (`:160`).** Off-canonical but ≈10.5:1 — legible, passes; pure drift. Should be `#94a3b8` (the canonical secondary, also a chart-tick color used at `:153`) for consistency — the screen uses `#94a3b8` for the X-axis ticks and `#cbd5e1` for the Y, an inconsistency with no rationale.
- **Status-color pairing on the delta strip is borderline (canonical §7 "never color alone").** The Increase/Decrease strip conveys direction by color (amber vs green) **and** a text label ("Increase"/"Decrease") + a signed value (`:201-203`), so it satisfies "pair color with text." Acceptable as-is; noting that the pairing is what saves it.

## Lens 4 — Regression-Across-Screens ("Does the same input produce the same number everywhere, and did this break another view?")
### Critical
- None. Step 2 reads `res.totalAllocated` (the cross-screen "current monthly" figure) straight from the engine (`:103, 106, 198`), so its "Current Monthly" cannot diverge from Step 1's budget total. The 11 slider values it writes are the single source other screens read.
### Improvement
- **`retMonthlySpend` re-sums the 11 sliders the engine already totals (Pattern-1 smell, convergent with the Step-3 finding).** `retMonthlySpend` (`:98-101`) = Σ 11 `ret*` sliders; the engine exposes `res.annualRetSpend` (= same 11 × 12). Same result today, no live divergence, but it is the **same recompute Step 3 does** — two screens independently re-adding the engine's `annualRetSpend`. If the spend definition changes (a 12th category), both drift together. **Fix: `const retMonthlySpend = res.annualRetSpend / 12;`** — and the identical fix on Step 3 would retire the pattern in both places. *Convergent (this + step3-your-number_v1 Lens 4).*
- **`currentValues` re-derives Step 1 category sums locally (`:33-45`) and drops `subscriptions` from misc** (see Lens 1). These power the chart only and don't feed other screens, so not a divergence — but they re-implement bucketing the engine could expose, and the dropped field makes the "Today" column inconsistent with the seeding logic.
